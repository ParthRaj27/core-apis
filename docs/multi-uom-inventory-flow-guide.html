What belongs where?

Organization Units

Defines the reusable unit itself and how quantities may be entered.

  • Name and symbol
  • Decimal precision
  • Fraction policy
  • Minimum and increment
  • Rounding policy

Product

Defines which units this product uses and how they convert.

  • Base inventory unit
  • Default sale/purchase units
  • Product-specific factors
  • Sale/purchase permissions
  • Optional unit barcode

Inventory

Stores one authoritative quantity for each product and location.

  • On hand in base unit
  • Reserved in base unit
  • Reorder level in base unit
  • Average cost per base unit
  • No separate Bag/KG stock pools

Purchase → inventory → sale

1

Purchase entry

User enters 5 Bags + 18 KG. The API verifies both units belong to Rice and that 1 Bag = 10 KG.

2

Server conversion

The API calculates (5 × 10) + 18 = 68 KG. The client cannot override this result.

3

Inventory posting

The selected warehouse receives 68 KG. The original mixed entry and conversion factors are snapshotted.

4

Partial sale

A customer buys 3 KG. Inventory becomes 65 KG.

5

Bag sale

Another customer buys 2 Bags. The API subtracts 20 KG; inventory becomes 45 KG.

Automatic pricing

Base price

Rice retail price is configured as KSh 120 per KG.

Bag price = 120 × 10 = KSh 1,200

Server remains authoritative

The desktop app shows a live preview, but the API calculates the final selected-unit price, tax, discount, and line total.

A client-supplied factor or total that differs from the server is rejected.

Rules that prevent incorrect stock

Allowed
Custom units, decimals, mixed entries, partial-package sales, automatic conversion.
Validated
Tenant ownership, positive factors, permitted operations, precision, increments, available stock.
Never guessed
Ambiguous legacy inventory, missing conversion factors, client-calculated authoritative totals.

Existing inventory migration

The current system may contain separate inventory rows by unit_id. They cannot be combined blindly because some quantities may already be converted.

1

Classify without changing data

Identify base, alternate, legacy-pack, and ambiguous rows.

2

Convert only proven quantities

Use confirmed product factors; never infer behavior from names like “Bag”.

3

Reconcile

On-hand, reserved, movement, and valuation totals must match before activation.

4

Enable organization safely

Switch to canonical base inventory only after the report passes. Ambiguous products remain blocked for correction.
